# Multi-drone simulation (Phase 1)

The fleet world is generated under `data/simulation_runs/multidrone_<session-id>/` from the same versioned profiles and world builder used by Simulation Lab. This directory does not contain a second, divergent SDF. The generated world includes `drone_01`, `drone_02` (or up to four configured vehicles), separate model names, per-vehicle camera topics, and Gazebo FDM ports `9002 + 10 × instance_id`. ArduPilot `sim_vehicle.py --count N --auto-sysid` provides matching independent SITL instances. The initial launch spacing is a validated fleet configuration value applied to both Gazebo model poses and SITL `--auto-offset-line`.

The fleet API is separate from the single-drone Mission API. Prepare a validated Mission coverage plan and its Simulation Lab scenario, then use `POST /api/multidrone/start` with the validated roster. `GET /api/multidrone/status` provides per-vehicle telemetry, frame counters, assigned sectors, progress, and freshness. `POST /api/multidrone/vehicles/{id}/return` requests that vehicle's existing bounded RTL; `POST /api/multidrone/stop` requests return for all active vehicles. The server shuts down each owned camera helper and the generated world when the runners finish.

The Phase 1 foundation flew partitioned search routes. Phase 2 added the shared survivor registry, exclusive assignments, and the existing safety-gated service executor. SEARCHER service requests remain forbidden in the backend. Camera observations retain session, vehicle, and frame provenance; an unconfirmed observation cannot directly authorize a delivery. The fleet UI counts confirmed canonical records, never raw detections.

Live qualification still requires both vehicles to pass GPS/home/EKF readiness and complete their assigned routes with adequate host memory. A process crash during a fleet run can orphan WSL children; operators must verify and clean the exact generated run's PIDs before restarting. No physical hardware path is provided.

## Phase 2C dispatch policy

The existing shared registry remains the only source of confirmed survivor identities. Explicit service priority is `CRITICAL > HIGH > NORMAL > LOW`; absent an operator or mission designation it is `NORMAL` with source `DEFAULT`. The detector's confidence never sets priority. Queued jobs sort by priority, confirmation time (oldest first), then canonical ID. `POST /api/multidrone/survivors/{canonical_id}/priority` accepts a validated enum value while a fleet is active and records `OPERATOR` provenance; trusted mission logic may call the coordinator with `MISSION` provenance. The backend emits an audit event. Active assignments are not preempted by a later priority change.

The coordinator's existing lock enforces one active job per survivor and one per SERVICER. Eligible SERVICERs must have fresh connected telemetry and be READY or SEARCHING, armed, and not returning; selection minimizes reported horizontal travel distance, breaking ties by vehicle ID. Targets with missing location, uncertainty over the existing 8 m approach gate, a camera observation not received within five minutes, or verified delivery remain unassigned with an explicit waiting reason. The receipt-time gate is separate from source timestamps and clears only on a genuinely new observation. A pre-release failure can requeue; once release occurs, a failed or ambiguous outcome cannot trigger another release. Completion only frees a SERVICER after the existing delivery-verification and search-resumption path.

`ground/backend/tests/test_multidrone_phase2c_genuine_live.py` is a separate opt-in real acceptance test. It requires an independently prepared, validated two-person Gazebo mission ID and an idle runtime; it never injects detections or terminates unrelated processes. Do not run it while another Gazebo/SITL session owns the world or ports. Its skip in routine automated tests is **not** live acceptance evidence.
